# Database (Supabase)

Everything the site shows and everything customers send lives in one
Supabase project: settings, the two sections, the site's texts, products and
their photos, the gallery, cake options, cake inquiries and their photos,
orders and payments, and the admin team.

- `migrations/` – the database: tables, security rules, photo storage.
- `seed.sql` – today's content from `src/content.js`, generated by
  `npm run db:seed-file`. Don't edit it by hand.
- `tests/` – checks of who can see and change what (`npm run db:test`).

## Who can do what

| | Visitors | Signed in, not invited | Editor | Owner |
|---|---|---|---|---|
| Read published products, texts, gallery, cake options | ✓ | ✓ | ✓ | ✓ |
| See hidden products | | | ✓ | ✓ |
| Change products, texts, photos, settings, cake options | | | ✓ | ✓ |
| See and handle inquiries, their photos, orders, payments | | | ✓ | ✓ |
| Press Publish, see the activity log | | | ✓ | ✓ |
| Invite and remove admins | | | | ✓ |

- **Customers never write to the database directly.** The site's server code
  (Cloudflare Functions, phase 4) checks the spam test and stores the inquiry
  with the service key, and gives the customer short-lived signed links to
  upload their photos into the private `inquiry-uploads` bucket.
- **The team always keeps at least one owner**, so nobody can lock everyone out.
- **Every change by an admin is logged** in `activity_log` with who made it.
- Site photos live in the public `public-media` bucket (readable, not
  listable); customers' photos are in the private `inquiry-uploads` bucket.

## Setting up the hosted project

1. **Create the project** at supabase.com: region *Mumbai (ap-south-1)*,
   a strong database password kept in a password manager.
2. **Create the database.** Either paste `migrations/*.sql` and then
   `seed.sql` into *SQL Editor* and run them, or with the command-line tool:
   ```sh
   npx supabase login
   npx supabase link --project-ref <project-ref>
   npx supabase db push
   psql "<connection string from Project Settings → Database>" -f supabase/seed.sql
   ```
3. **Switch off public sign-ups:** *Authentication → Sign In / Providers →
   Email*: turn off *Allow new users to sign up*. Keep *Confirm email* on.
   Set the minimum password length to 8 and turn on *Leaked password
   protection* if the plan offers it.
4. **Set the addresses** under *Authentication → URL Configuration*:
   *Site URL* `https://<domain>`, and add `https://<domain>/admin/` (plus
   `http://localhost:5173/admin/` for local work) to *Redirect URLs*.
5. **Make the owner an admin.** In *SQL Editor*:
   ```sql
   insert into public.admin_invites (email, role) values ('owner@example.com', 'owner');
   ```
   then *Authentication → Users → Invite user* with the same email. She
   chooses a password from the email and signs in at `/admin/`. Invite more
   admins the same way, with role `editor` (or `owner`).
6. **Send login emails through Resend** (Supabase's own mail service only
   sends a few an hour): *Authentication → Emails → SMTP Settings* with host
   `smtp.resend.com`, port 465, user `resend`, the Resend API key as the
   password, and a sender on the verified domain.
7. **Give the site the project's address and publishable key.** In Cloudflare
   Pages (*Settings → Variables*) and in a local `.env.local` (see
   `.env.example`):
   ```
   VITE_SUPABASE_URL=https://<project-ref>.supabase.co
   VITE_SUPABASE_PUBLISHABLE_KEY=<publishable or anon key>
   ```
   The **service (secret) key** is only ever stored as a Cloudflare secret
   for the server code. Never put it in a `VITE_` variable or in the code.

8. **Upload the site's current photos** into the `public-media` bucket, once,
   from your own computer (the service key stays there):
   ```sh
   SUPABASE_SERVICE_KEY=<service key> npm run db:upload-photos
   ```
9. **Set up publishing** in Cloudflare Pages: *Settings → Builds → Deploy
   hooks*, add a hook for the production branch, and save its address as the
   secret `DEPLOY_HOOK_URL` (*Settings → Variables and secrets*). Also set
   `SITE_URL` to the site's address. The admin panel's Publish button calls
   `functions/api/publish.js`, which checks the person is an admin and then
   calls the hook.

## How content reaches the site

The site is built from the database, not read from it while visitors
browse: `npm run build` first runs `npm run content`
(`scripts/fetch-content.mjs`), which reads what visitors may see with the
publishable key, downloads any new photos and writes
`src/content.generated.js`. Without Supabase settings it uses
`src/content.js` instead, so the site still builds on its own.

The texts and sections refer to photos by product (its slug), so replacing a
product's photo updates every place it appears. A hidden product drops out
of lists; a slot that needs one photo shows another from the same section
and the build prints a warning.

## Changing the database later

Add a new file to `migrations/` (named `<timestamp>_<what>.sql`); never edit
one that has already been applied. Run `npm run db:test`, then
`npx supabase db push`.

`npm run db:test` needs Postgres 15 or newer installed locally. It loads a
small stand-in for Supabase's own parts (`tests/supabase-stub.sql`), the
migrations and the seed into a throwaway database, and checks the access
rules for visitors, uninvited accounts, editors and owners.
